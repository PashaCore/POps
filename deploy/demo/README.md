# POps public demo

A read-only POps panel full of fake school computers, meant for `https://demo.pashacore.com.tr`. Anyone can sign
in as **demo / demo** and look at every page a viewer can see; nothing can be changed. Everything is wiped and
rebuilt every night at 03:30.

| Service | What it runs | Reachable from |
|---|---|---|
| `db` | PostgreSQL 17 (small settings: 64 MB shared buffers, 40 connections) | internal network only |
| `backend` | the POps backend image, with `POPS_DEMO_USERS=demo` | internal network only |
| `dashboard` | the POps panel image (Apache + PHP), with `POPS_DEMO_LOGIN=demo:demo` | `127.0.0.1:8180` on the host |
| `fleet` | [`tools/demo_fleet.py`](../../tools/demo_fleet.py) on the backend image, mounted read-only | internal network only |
| `seed` | [`seed.py`](seed.py), one-off, run by `reset.sh` | internal network only |

## What a visitor sees

- **50 computers**: Bilişim Lab 1 (16), Bilişim Lab 2 (16), Fen Lab (10), Kütüphane (6) and two teacher PCs
  (`BL1-PC01` … `KUT-PC06`, `BL1-OGRETMEN`, `FEN-OGRETMEN`). Each lab has its own hardware (Core i3/i5/i7,
  Ryzen 5, 8–16 GB, 256 GB–1 TB SSD) and Windows 10 Pro 22H2 or Windows 11 Education/Pro 24H2, about 40 school
  programs with versions (browsers, Office, LibreOffice, GeoGebra, Scratch, Python, VLC, 7-Zip, Notepad++, …) and a
  Windows Update status: six PCs have pending or not-yet-rebooted updates.
- **A school day** in local time (`TZ`): students sign in during lessons (online), PCs sit idle in breaks, and in the
  evening, at night and at weekends about 60 % are off. A few PCs drop off and come back during the day.
- **Things happen**: one PC (`BL2-PC07`) quarantines itself after three DNS violations right after it enrolls;
  during lessons there are 1–2 DNS violations an hour, the odd failed sign-in and help-desk tickets sent from the
  tray. Three PCs run the previous agent version, one reports agent errors, and the teacher PCs have remote screen
  turned off on the device.
- **Two weeks of history**: sign-ins, violations, an exam-time quarantine, a self-quarantine that IT lifted, an
  agent update with one rollback, scheduled and manual jobs with their outputs, remote-screen sessions, tickets,
  notifications, three licences (one over-used, one expiring) and three schedules.

The fleet behaves like real agents: it enrolls with a token, gets a per-device secret, sends heartbeats, inventory,
software and update status, and answers the panel. It **never executes anything**: every command gets a canned
reply (see the header of `tools/demo_fleet.py`).

## Read-only and isolated

- **The demo account cannot change anything.** It has the `viewer` role, so admin pages and endpoints are closed,
  and the backend treats it as a demo account (`POPS_DEMO_USERS`, see
  [`docs/configuration.md`](../../docs/configuration.md#public-demo-read-only-accounts)): every request other than
  `GET`/`HEAD`/`OPTIONS`, its own password and 2FA included, returns `403 Demo hesabında değiştirilemez`.
  `Backend/tests/test_demo.py` checks every write endpoint in the route table.
- **Network.** The database, backend and fleet are on an internal Docker network with no route out and no
  published ports. Only the panel publishes a port, on `127.0.0.1:8180`; the host's Apache is the public entry.
- **Containers.** `no-new-privileges` everywhere; the backend, fleet and seed drop all capabilities and run as a
  non-root user; the fleet's root filesystem is read-only. Memory and process limits (`mem_limit`, `pids_limit`) and
  log rotation keep the demo from crowding the host. The only host files mounted are `tools/` and `seed.py`,
  read-only. It is a separate Compose project (`pops-demo`) with its own volumes and networks.
- **Secrets** (database password, JWT key, enrollment token, admin password) are generated by `setup-host.sh` into
  `.env.demo` (mode 600). The file is git-ignored and never enters an image (`.dockerignore` excludes `deploy/`).
  The enrollment token is stored only as a hash, is valid for two days and for exactly as many enrollments as the
  fleet has PCs.
- **Nightly reset.** `reset.sh` removes the containers, the database and the fleet's state (`down -v`) and builds the
  demo again, so nothing anyone does survives the night.
- **Admin.** A superadmin (`yonetici`) with a random password exists for the owner; `setup-host.sh` prints the
  password once and keeps it in `.env.demo`.

## Install (owner, once)

The host already runs Docker with Compose v2, Apache under Virtualmin, and the DNS record is in Cloudflare
(proxied).

**1. Run the setup script as root**, with a release tag that contains `deploy/demo/` (or `main`; `main` if omitted):

```bash
git clone https://github.com/PashaCore/POps.git /opt/pops-demo
sudo bash /opt/pops-demo/deploy/demo/setup-host.sh v0.1.22-alpha
```

It is short and every step can be repeated: (1) checks out the tag in `/opt/pops-demo`, (2) creates `.env.demo`
with random secrets (mode 600; kept on later runs), (3) pulls the images from GHCR, or builds them from the checkout
when that tag is not published, and runs `reset.sh` (`docker compose -p pops-demo up`, migrate, seed, fleet),
(4) installs `pops-demo-reset.service` and `pops-demo-reset.timer` (03:30 every night), (5) prints the Apache step
below and, the first time, the admin password.

**2. Create the site in Virtualmin and point it at the demo:**

```bash
virtualmin create-domain --domain demo.pashacore.com.tr --parent pashacore.com.tr --dir --web --ssl --logrotate
WEB=$(virtualmin list-domains --domain demo.pashacore.com.tr --home-only)/public_html
OWNER=$(virtualmin list-domains --domain demo.pashacore.com.tr --user-only)
rm -f "$WEB/index.html"
install -m 644 -o "$OWNER" -g "$OWNER" /opt/pops-demo/deploy/demo/demo.htaccess "$WEB/.htaccess"
virtualmin generate-letsencrypt-cert --domain demo.pashacore.com.tr --renew
```

`--parent` makes it a sub-server of the existing account, so no password or Unix user is needed; `--dir` is still
required because a website needs a home directory (`virtualmin help create-domain`). The `.htaccess` uses the same
`[P]` rewrite technique as `Installer/server/apache-htaccess.example` and needs `mod_rewrite`, `mod_proxy`,
`mod_proxy_http` and `mod_proxy_wstunnel` (for `/ws/`), all already used by the dev site. Its content
(`demo.htaccess`):

```apache
# POps public demo: the whole site is the demo stack on 127.0.0.1:8180 (deploy/demo/docker-compose.demo.yml).
# Goes into the Virtualmin site's public_html as .htaccess. Needs mod_rewrite, mod_headers, mod_proxy,
# mod_proxy_http and mod_proxy_wstunnel (the same modules the dev site's .htaccess uses).
# Delete Virtualmin's default index.html from public_html, or it is served instead of the panel.
RewriteEngine On

# The panel marks its cookies Secure when it knows the visitor came over HTTPS
<IfModule mod_headers.c>
    RequestHeader set X-Forwarded-Proto "https"
</IfModule>

# Let's Encrypt (HTTP-01) is answered from public_html itself, never proxied
RewriteCond %{REQUEST_URI} ^/\.well-known/acme-challenge/
RewriteRule ^ - [L]

# WebSocket (live panel updates). %1 comes from the LAST matched condition, so the path condition goes last
RewriteCond %{HTTP:Upgrade} websocket [NC]
RewriteCond %{REQUEST_URI} ^/ws/(.*)$
RewriteRule ^ ws://127.0.0.1:8180/ws/%1 [P,L,NS]

# Everything else: panel, /api, assets
RewriteCond %{REQUEST_URI} ^/(.*)$
RewriteRule ^ http://127.0.0.1:8180/%1 [P,L,NS]
```

If you change `POPS_DEMO_PORT` in `.env.demo`, change `8180` here too.

**3. Cloudflare:** keep the record proxied and set SSL/TLS encryption mode to **Full**. Let's Encrypt's HTTP-01
check passes through the proxy because the `.htaccess` leaves `/.well-known/acme-challenge/` to Apache.
(**Full (strict)** also works once the Let's Encrypt certificate is installed.)

Check: `curl -sI https://demo.pashacore.com.tr/login` returns `200`, and the page shows
"Demo: kullanıcı demo, şifre demo (salt okunur)".

## Operate

```bash
cd /opt/pops-demo/deploy/demo
dc() { docker compose -p pops-demo --env-file .env.demo -f docker-compose.demo.yml "$@"; }
dc ps                                   # db, backend, dashboard healthy; fleet running
dc logs --tail 20 fleet                 # every 5 minutes: online / idle / off / enrolled
sudo systemctl start pops-demo-reset    # reset now (same as the nightly run)
systemctl list-timers pops-demo-reset.timer
sudo bash setup-host.sh v0.1.23-alpha   # move to a new release (keeps .env.demo, resets the demo)
```

To remove it: `systemctl disable --now pops-demo-reset.timer`, delete the two unit files in
`/etc/systemd/system/`, run `dc down -v --rmi all`, delete `/opt/pops-demo`, and
`virtualmin delete-domain --domain demo.pashacore.com.tr`.

## Resource use

Measured on the test run (all 50 PCs connected, idle panel): backend 61 MiB, PostgreSQL 49 MiB, panel 25 MiB,
fleet 27 MiB, about **160 MiB** in total and under 1 % of one CPU core. The limits are 384 / 384 / 256 / 128 MiB.
Images: backend 297 MB, panel 714 MB, plus `postgres:17`. A full reset (wipe, start, migrate, seed) takes about
30 seconds; the fleet has enrolled 20 seconds later.

## Settings (`.env.demo`)

| Variable | Default | Meaning |
|---|---|---|
| `POPS_IMAGE_TAG` | the checked-out tag without `v` | GHCR image tag; built locally when not published |
| `POPS_DEMO_PORT` | `8180` | panel port on `127.0.0.1` |
| `TZ` | `Europe/Istanbul` | school calendar and timestamps |
| `DB_NAME`, `DB_USER`, `DB_PASS` | `pops_demo`, `pops_demo`, random | database |
| `JWT_SECRET` | random | panel session key |
| `PANEL_ADMIN_USER`, `PANEL_ADMIN_PASS` | `yonetici`, random | the owner's superadmin |
| `POPS_DEMO_USERS` | `demo` | read-only accounts (backend) |
| `POPS_DEMO_LOGIN` | `demo:demo` | account shown on the sign-in page and created by `seed.py` |
| `DEMO_ENROLL_TOKEN` | random | the fleet's enrollment token |
| `DEMO_FLEET_SCHEDULE` | `school` | `always` keeps every PC on (testing) |
| `DEMO_FLEET_NIGHT_ON` | `0.4` | share of PCs left on in the evening, at night and at weekends |
| `DEMO_FLEET_HB` | `10` | heartbeat interval in seconds |
